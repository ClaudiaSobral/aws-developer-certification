# 0.1 Introduction to being an AWS Developer

## Objetivo do módulo:

- Descrever as responsabilidades de um Developer AWS e como elas se diferenciam das de um developer tradicional
- Comparar diferentes opções de computação AWS para diferentes casos de uso
- Identificar prós e contras entre computação serverless, containers e máquinas virtuais para APIs
- Avaliar custos, performance e escalabilidade ao escolher plataformas de computação
- Aplicar frameworks de decisão para selecionar os serviços AWS apropriados com base nos requisitos específicos
- Aplicar convenções de nomeação e de estratégia de gestão de recursos
- Usar ferramentas IA, como o Kiro, para gerar, revisar e otimizar o código

## Resumo do módulo

- Cada plataforma tem seus prós e contras que criam um efeito cascata em todo o projeto:
    - Serveless elimina gestão de infraestrutura, mas introduz *cold start* na equação
    - Containeres dão flexibilidade de deployment, mas torna necessário ter expertise de orquestração
    - Máquinas virtuais oferecem controle total, mas mais custos operacionais no gerenciamento de infraestrutura

- Lambda funciona bem para operações CRUD pay-per-use. Containeres ECS funcionam para projetos que demandam muita performance

- Responsabilidades do AWS Developer
    - Um developer AWS trabalha junto com o arquiteto de soluções (que fica mais na part de definir os requisitos da aplicação) e do DevOps, responsável pela esteira de CI/CD. Ainda assim, o developer deve compreender como seu trabalho impacta o trabalho do arquiteto e do DevOps.
    - Você precisa lidar com escolhas de arquitetura: serviço de computação, armazenamento e integração de código. Além disso, você vai tratar de desenvolvimento de código, integração de infraestrutura com código (Infrastructure as Code), além de se preocupar com as melhores práticas de segurança através do IAM, encriptação e comunicação segura entre serviços.
    - Algumas de suas responsabilidades operacionais são monitoramento, debugging e gerenciamento otimizado de custos 

## Workflow do desenvolvimento

AWS CLI -> SDKs -> CDKs -> Amazon Q/Kiro

### AWS CLI

- Acessa diretamente serviços da AWS através de linha de comando. O CLI serve para coisas muito pontuais e imediatas.
- Principais usos:
    - Deploy de aplicações e infraestrutura
    - Gerenciamento de recursos AWS de forma programática
    - Automação de scripts de deployment e integração com integração contínua e delivery contínuo (CI/CD)
    - Fazer *queries* sobre status de serviços e configuração de recursos

### AWS SDK (Software Development Kit)
- SDK é pra quando precisamos fazer o código interagir com a arquitetura
- Acesso programático aos serviços AWS através dos códigos de preferência (atualmente Python, JavaScript, Java, C#, Go, Ruby, PHP e outras linguagens populares de programação)
- SDK interage com as aplicações que já existem na nuvem.
- Roda em *runtime*
- Chama APIs da AWS
- Integração segura com serviços AWS:
    - Inicializar os serviços com as credenciais e regiões corretas
    - Administrar apropriadamente as respostas de serviço e condições de erro
    - Implementar lógica de retry para falhas transitórias
    - Usar padrões async/wait para operações non-blocking (operações que o resto do código pode rodar enquanto uma task está em andamento)

### AWS CDK (Cloud Development Kit)
- O CDK também provisiona serviços, mas seu propósito é voltado para infraestrutura no processo de produção, aplicando blocos estruturados repetíveis ao longo de toda arquitetura.
- Define infraestrutura de serviços na nuvem utilizando linguagens familiares de programação em vez de YAML ou JSON apenas.
- Usos primários:
    - Definir infraestrutura com linguagens populares, como TypeScript, Python, Java, C# ou Go
    - Infraestrutura com controle de código de versão
    - Usar linguagem de programação com loops
    - Compartilhar e reutilizar blocos de código na infraestrutura de todo o projeto
- Fluxo de trabalho:
    - Escrever código usando linguagem preferida
    - Usa construtos CDK para representar recursos AWS
    - Sintetizar código CDK em templates CodeFormation
    - Fazer deploy por vias mais familiares de código


### Amazon Kiro
- É basicamente uma IDE muito similar ao VSCode, integrando CLI e CDK. Ele contém uma inteligência artifical agêntica que ajuda a criar código em linguagem natural. 
- É preciso ter certeza de que o Kiro está com acesso de leitura ao arquivo alvo antes de fazer a pergunta.
- Ele pode ser um ponto de partida, mas devemos revisar o código tal como se o tivéssemos escrito.

### Ferramentas de teste local
- AWS Serverless Application Model Command Line Interface (AWS SAM CLI): testa localmente funções Lambda e de API Gateway
- LocalStack: roda serviços AWS localmente para teste
- Docker: conteineriza aplicações

### Integrações com IDE
- AWS Toolkit: extensão disponível para várias IDEs populares
- Syntax highlighting: disponível para AWS CloudFormation, templates AWS SAM e comandos CLI
- Suporte a debbug: para funções Lambda localmente

### Model Context Protocol (MCP)
- É uma ferramenta na qual o Kiro se conecta para extender suas capacidades agênticas, se conectando a serviços AWS.

## AWS Developer Role and Compute Platforms

- Existem três diferentes escolhas de serviço de computação: AWS Lambda (serverless), Amazon ECS (container), EC2 (máquina virtual). Nessa parte do módulo, aprendemos qual escolha fazer em qual situação.

- Lambda:
    - Tarefas stateless que rodam em menos de 15 minutos. Se não, outro serviço
    - Tarefas event-driven
    - Escala automaticamente de 0 a milhares
    - Paga por requisição e não paga tempo ocioso (idle time)
    - Máximo de 15 minutos por invocação
    - Integrado com outros serviços AWS nativamente
    - Ideal para tarefas pontuais ou que escalam em picos, como resize de upload de fotos ou processamento de atualização de pedidos
    - Não é adequada para tráfegos muito grandes, pois o custo por invocação pode não ser benéfico. Trocar pra Fargate nesse caso.
    - Lambda pode ter problemas com *cold start*
- ECS/EKS:
    - Tarefas que rodam em mais de 15 minutos ou são statefull
    - Orquestra containers Docker. Fargate os hospeda de forma serverless
    - Alocação flexível de recursos
    - Integração com load balancers e discovery services
    - Escolher entre Fargate (não gerenciamos host) ou EC2 (totalmente gerenciado)
    - Se o time estiver todo em AWS -> ECS. Se não, EKS (Kubernetes)
    - Ideal para arquitetura em microsserviços, aplicações que requeiram runtime, processos longos (acima de 15 minutos) ou times que já fazem conteinerização
- EC2:
    - Controle completo do ambiente
    - Ampla variedade de instâncias para diferentes cargas de trabalho
    - Armazenamento persistente
    - Suporta qualquer linguagem ou framework
    - Precisa que você faça patches, determine regras de scaling e disponibilidade
    - Ideal para aplicações legadas, aplicações que demandam hardware específico, workloads que precisam de performance previsível e para times que precisam de controle total da arquitetura.
- É necessário escolher um! Trabalhar com uma arquitetura híbrida no início é uma escolha ruim. É melhor escolher um, conhecer o workload e ir evoluindo o serviço

- Nessa ordem, você ganha mais controle e mais custos operacionais (overhead). Indo no sentido inverso, menos controle e menos custos operacionais.

- Não escolhemos uma plataforma para todos os serviços. ❗❗❗❗ESCOLHEMOS POR COMPONENTE❗❗❗❗

Como começar a escolher:
- Pensar na carga de trabalho:
    - Previsível ou imprevisível?
    - Alto tráfego ou baixo tráfego?
- Então pensar em custos de latência
    - Você pode lidar com cold start? Se sim, Lambda. Se não, Lambda não é a escolha, a não ser que se possa pagar por concorrência provisionada

## Architectural Decision Frameworks

- Esse framework se baseia no AWS Well Architected Framework
    - Excelência operacional
    - Segurança
    - Confiabilidade
    - Eficiência de performance
    - Otimização de custos
    - Sustentabilidade

- A decisão do Developer é ver qual pilar é mais importante para a decisão em jogo

- É importante documentar decisões! Amazon Q pode ajudar nessas escolhas e documentações.
